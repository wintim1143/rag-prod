# 摄入流程说明（Ingestion Flow）

回答三个问题：**新增文件到向量库的流程是什么 / 只能解析纯文本吗（支持 PDF 吗）/ 是否需要 LLM 参与。**

## 1. 完整流程（五步）

```
① 加载(Load)    ② 解析归一(Parse)    ③ 切分(Split)    ④ 向量化(Embed)    ⑤ 写入(Store)
文件 ────────► 正文+元数据 ────────► 语义块 ────────► 向量 ────────► LanceDB
```

1. **加载** — 按文件类型分派到对应加载器，把二进制/结构化文件读进来。
2. **解析归一** — 抽取正文文本 + 元数据（标题、源路径、章节路径、上传时间、租户标签等），统一成「文档对象」。
3. **切分** — 用标题感知 / 递归字符切分器切成有语义边界、带 overlap 的块（保留章节上下文）。
4. **向量化** — 每个块调 **Embedding 模型**（专用模型，不是 chat LLM）变成向量。
5. **写入** — 向量 + 正文 + 元数据一起写入 LanceDB，按 `docId` 管理（重复摄入 = 更新而非重复）。

生产形态中，`/ingest` 是**异步**的：上传后返回 job id，轮询进度（大文档处理耗时）。

## 2. 只能解析纯文本吗？支持 PDF 吗？

**不是纯文本**。框架加载器原生覆盖多格式：

| 格式 | 加载器方式 |
|---|---|
| `.txt` / `.md` | 原生文本读取；Markdown 可做标题感知切分、剥离 frontmatter |
| `.pdf` | 抽取**文本层**（数字生成的 PDF）；配合标题/表格保留 |
| `.docx` | 抽取段落与表格文本 |
| `.html` | 抽取正文（去标签、去导航） |

**PDF 要区分两种**：

- **文本型 PDF**（文字可选中/复制）→ 直接抽文本，**不需要 OCR**。
- **扫描件/图片型 PDF**（纯图片，文字不可选）→ 文本层为空，需要 **OCR**（本地 tesseract.js，或云文档 AI）。OCR 属于可选项，成本高、准确率有上限，默认不做；遇到扫描件再按需开启。

> 原则：加载器只负责「把内容变成可检索的文本 + 元数据」。表格、版式这类结构信息会尽量以可读文本形式保留，但不会 100% 还原排版——检索质量优先于版式还原。

## 3. 是否需要 LLM 参与？

**核心流程不需要 chat LLM。** 摄入只有 **Embedding 模型**参与（它和生成用的 LLM 是两回事——Embedding 是专用小模型，负责「文本→向量」，不生成内容）。默认摄入链路是 **LLM-free** 的，这也是为了控制成本：文档量大时每篇都调 LLM 会显著烧钱。

**LLM 可选的增强（按需开启，各有代价）：**

| 增强 | 做什么 | 代价 |
|---|---|---|
| 上下文感知分块 | LLM 判断语义边界再切块 | 每篇多次 LLM 调用 |
| 块摘要（小转大 / parent-child） | 块内嵌摘要向量、存全文，检索粒度细但生成上下文全 | 双份 embedding |
| 元数据补全 | LLM 生成标题/摘要/标签 | 每篇 1 次调用 |
| 表结构理解 | LLM 把复杂表格转成可检索文本 | 每表调用 |

**结论**：默认先走「零 LLM」的纯加载→切分→embedding→存储；只有当检索质量不足、且诊断（07）指向分块/内容表达问题时，才按需加其中某一项增强。embedding 与重排是检索质量的主要放大器，LLM 增强是次选。

## 与诊断/评估的呼应

- 摄入质量直接决定「为什么检索不准」——如果文档解析丢了章节标题、或切分切断了语义，检索就召回不到正确块。用 07 的诊断工具可定位是「加载丢了内容」还是「切分切碎语义」。
- 改分块参数/解析策略后，用 06 的评估回归对比确认收益，避免凭感觉调参。
